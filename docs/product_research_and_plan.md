## 1. 背景调查与行业趋势

### 1.1 现代团队的“会议资产流失危机”

随着远程分布式协作与混合办公（Hybrid Work）成为全球软件开发与知识密集型企业的常态，会议的频次呈指数级上升。然而，组织协同效率并没有因会议增多而线性提升，反而陷入了深重的“会议资产流失危机”：

```
      ┌─────────────────────────────────────────────────────────────┐
      │                 传统会议流失闭环 (The Leak Loop)              │
      └─────────────────────────────────────────────────────────────┘
          会前准备缺失               会中记录混乱               会后跟踪断层
     ┌──────────────────┐      ┌──────────────────┐      ┌──────────────────┐
     │ • 议程目标不明晰   │ ───► │ • 原始笔记碎片化   │ ───► │ • 决议无法查证   │
     │ • 资料零散未对齐   │      │ • 打字与思考冲突   │      │ • 待办未责任到人 │
     │ • 缺乏时间预期     │      │ • 产出无结构化沉淀 │      │ • 进度脱节被遗忘 │
     └──────────────────┘      └──────────────────┘      └──────────────────┘
               ▲                                                           │
               └───────────────── 重新开会核对对齐 ◄────────────────────────┘
```

1. **会前脱节**：缺乏统一且具有时序约定的周期性议程，参会者常在“零背景输入”状态下参会，会议前期大量时间被消耗在基础信息同步上。
2. **会中记录混乱与摩擦**：速记人员与核心参会者在“自由文本快速录入”与“结构化表单规范填写”之间左右为难。纯文本 Markdown 最契合人类打字心流，但无法提供强约束的实体；而打开重型项目管理系统录入表单又会严重打断会议进程。
3. **会后流失与决策沉睡**：会议结束后，纪要往往被封存在个人的本地记事本或分散在各 IM 群聊的历史记录中。关键决策（Decisions）缺乏版本化追溯链条，行动项（Action Items）缺乏清晰的分配、排期与闭环状态，导致团队陷入“开会讨论 → 形成口头共识 → 无人跟进 → 发生事故 → 再次开会”的无限低效循环。

### 1.2 商业 SaaS 的天花板与隐忧

市面上主流的商业 SaaS 产品（如飞书会议/妙记、Notion、Otter.ai、Fireflies.ai、腾讯会议/企微）提供了高度封装的智能转写和云端协同能力，但在企业深水区应用中暴露出愈发严重的结构性缺陷：

| 评估维度 | 商业 SaaS 解决方案现状 | 深度隐患与核心痛点 |
| :--- | :--- | :--- |
| **数据主权与隐私** | 核心录音、逐字稿、未公开财报、核心架构决策全部上传公有云多租户环境 | 金融、国防、高端制造、出海法务合规（GDPR/等保三级）无法过审；存在敏感商业机密被用于第三方公有大模型训练的巨大风险 |
| **数据孤岛与供应商锁定** | 依赖厂商私有存储格式与专有云 API，导出为无状态只读 PDF/HTML | 历史资产难以低成本完整迁移；跨系统自动化对接困难；无法与内网自建代码库、工单系统深度集成 |
| **席位税与成本激增** | 普遍采用基于“人头/月”（Seat-based）的阶梯收费（每人每月 $10 ~ $30 不等） | 团队规模扩展时 IT 预算激增；临时或轻度参会人员同样需要付费席位，投入产出比极低 |
| **系统复杂度与臃肿度** | 功能大包大揽（融合了即时通讯、邮箱、复杂多维表格、云文档） | 学习曲线陡峭；团队往往只需要一个专注的会议资产闭环工具，却被迫承担笨重系统的运维与认知负荷 |

### 1.3 自托管轻量级会议流的“巨大市场空白”

在全球开源生态与数字化主权回归的浪潮下，**自托管（Self-Hosted）**、**轻量级（Lightweight）**、**专注会议流与待办闭环（Meeting Flow & Outcome-Driven）** 的工具存在显著的市场断层：
- 重型开源协同套件（如 Nextcloud、GitLab + Mattermost 矩阵）部署动辄需要 Kubernetes、PostgreSQL、Redis、ElasticSearch 等复杂组件，运维成本居高不下；
- 个人知识库工具（如 Obsidian、Logseq）专注于个人本地双链，缺乏多用户工作区隔离、周期性会议排期引擎与组织级待办权限边界；
- **行业呼唤一款真正单容器启动、零外部外部依赖、天然支持 Markdown 心流且具备企业级决策/待办实体双向联动的协同中枢**。这正是 MeetFlow 具备核心竞争力的战略生态位。

### 2.1 开源生态标杆全景对比

为准确定位 MeetFlow 的独特性，我们将其与开源协同领域的四大标杆系统进行横向架构级对比：

| **核心定位** | 看板式项目管理 (Trello/Notion Boards 替代) | 团队企业级知识库 Wiki (Notion/Confluence 替代) | 客户端优先个人/小团队笔记 (Notion 替代) | 个人端到端加密笔记 | **轻量多人共享会议档案与决策待办闭环系统** |

| **会议周期系列** | ❌ 无 | ❌ 无 | ❌ 无 | ❌ 无 | **✅ 内置 MeetingSeries 周期规则引擎与自动创建槽位** |

### 2.2 核心断层剖析：Markdown 原始手记与结构化决议/待办分离双向联动的行业缺失

在协同办公领域，长期存在着**“自由录入心流”**与**“严谨数据流转”**的不可调和的矛盾：

```
      ┌─────────────────────────────────────────────────────────────┐
      │          行业典型妥协方案对比 (Compromise vs MeetFlow)       │
      └─────────────────────────────────────────────────────────────┘
  方案 A：纯文本标记法 (Obsidian / Outline)
  Markdown: "- [ ] 张三下周完成接口"  ──► 仅为纯文本符号，无法全局检索、无法排期、无法通知催办。
  
  方案 B：重型表单微件 (Jira / Linear / ClickUp)
  每次录入: 弹出弹窗 ──► 选项目 ──► 填标题 ──► 选经办人 ──► 选排期 ──► 严重阻断会议实时发言。
  
  方案 C：当前 MeetFlow 代码初版 (单向抽取锁死)
  Markdown: "@行动: 完成接口联调"  ──► 解析生成 ActionItem ──► 锁死为 derived_outcome_read_only
  缺陷: 用户在行动项看台无法打勾完成，无法改派人员，无法设置截止期，形成数据死锁。
  
  ★ 终极解法：MeetFlow 双向映射状态机 (Bi-directional State Machine)
  ┌────────────────────────┐                   ┌────────────────────────┐
  │  Markdown 原始文本      │ ◄─── 双向同步 ───► │   结构化数据库实体      │
  │ @行动:[todo][@张三] 接口 │      状态机       │  ActionItem (id, state,│
  │                        │                   │  owner=张三, due_date) │
  └────────────────────────┘                   └────────────────────────┘
```

- **现状之痛**：绝大多数工程师与产品经理极其依赖 Markdown 进行速记。但在现有工具中，一旦会议结束，这些笔记就像“死文字”一样躺在文档里；若想进行任务跟踪，又必须人肉将内容一条条复制到 Jira、Teambition 或 Trello 中。
- **双向割裂**：即使有部分系统尝试从 Markdown 中提取任务，通常也只是**单向生成**。一旦在待办看板中将任务标记为“已完成”，原始 Markdown 文档并不会得到更新；反之，若在文档中删改文字，又可能导致数据库中的关联任务被意外级联删除或状态混乱。
- **MeetFlow 的技术攻坚点**：构建一套能够在单机事务保证下，精准识别行级语法扩展、支持 AST 增量 Diff、双向事件派发与防冲突回写的**双向映射状态机**。

## 3. 产品定位与核心杀手级特点

### 3.1 产品核心定位

**MeetFlow** 是一款专为敏捷产研团队、极客组织及注重数据隐私与自主权的企业打造的**“轻量级多人共享会议档案、结构化行动项追踪与团队知识沉淀系统”**。它摒弃了冗余复杂的巨石架构，将注意力彻底聚焦在会议这一组织最高密度的沟通场景上，实现从“会前议程规划 → 会中沉浸速记 → 会后决策定稿与待办流转”的全生命周期闭环。

### 3.2 四大核心杀手级亮点

```
                     ┌──────────────────────────────────┐
                     │     MeetFlow 核心杀手级架构体系    │
                     └──────────────────────────────────┘
                                      │
         ┌──────────────────┬─────────┴────────┬──────────────────┐
         ▼                  ▼                  ▼                  ▼
  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
  │ 轻量单容器    │   │ 零外部依赖    │   │ 双向映射状态机│   │ 内置安全沙箱  │
  │ Single Docker│   │ Zero Ext-Dep │   │ Bi-Sync Engine│   │ Plugin Sandbox│
  │ • Python 3.12│   │ • SQLite WAL │   │ • 行级语法扩展│   │ • Manifest v2│
  │ • Vue 3 前端 │   │ • 内置 Worker│   │ • 增量 AST Diff│   │ • 边界上下文 │
  │ • 内存 <100MB│   │ • 内存状态机 │   │ • 看板/手记共振│   │ • 凭证密文隔离│
  └──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
```

1. **轻量自托管单容器（Single Docker Container）**：
   - 生产环境仅需单一容器（`ghcr.io/mcocdaa/meetflow:latest`），单条 `docker run` 命令挂载 `./data` 目录即可投入生产，内存常驻开销低于 100MB，支持快速冷启动与秒级灾备迁移。
2. **零复杂外部依赖（Zero External Overhead）**：
   - 彻底摒弃 Postgres、Redis、RabbitMQ 等多组件运维负担。利用现代嵌入式 SQLite 的高并发 WAL 模式作为数据主引擎，应用内协同驱动单进程 Worker 与轻量轮询/SSE 流，实现工业级稳定性的同时提供极致简单的运维体验。
3. **Markdown 原始手记与结构化决议/待办任务双向映射状态机**：
   - 原创设计行级语义标记（如 `@行动:[done][@alex][2026-10-01]: 重构支付网关` 与 `@决策: 采用方案B`）。
   - 用户既可以在编辑器中以极致打字心流完成记录，也可以在待办列表/看台中一键打勾、拖拽指派；系统底层通过 AST 解析器与事件总线保持两端实时一致，彻底终结自由笔记与结构化流转的割裂。
4. **内置安全沙箱插件机制（Security Sandbox Plugin Platform v2）**：
   - 插件采用严密的 Manifest 声明规范，提供精确的权限能力（`actions`, `exporters`, `event_subscriptions`, `ui_slots`, `context_scopes`）白名单；
   - 插件仅能访问服务端注入的受限上下文（Bounded Context），敏感凭据经过 AES-256 密文存储，事件通过带指数退让的 Outbox 事务保障最终一致性。

### 4.2 核心应用场景与标准工作流

#### 场景一：产研团队敏捷周会与架构评审（Focus & Live Sync）
1. **会前自动铺路**：由 `MeetingSeries` 周期规则自动创建本周固定槽位会议，预填固定站会站位议题（Standing Items），参会成员提前在待办看台中提报讨论议题。
2. **会中时间推进与沉浸记录**：
   - 负责人点击“开始会议”，进入专注工作台；
   - 议题自带倒计时时钟，当前议题耗时实时计算；
   - 记录员在 Markdown 记录区键入讨论细节，随时使用 `@行动:` 与 `@决策:` 语法捕获共识；
   - 点击“完成议题并进入下一项”，系统自动推进议程队列。
3. **会后快照封存与待办分发**：
   - 点击“结束会议”，系统在单事务中收敛未完议题为“已跳过”，持久化计算总耗时，创建只读 `MeetingSnapshot` 快照；
   - 派生出的待办自动出现在责任人的个人待办清单与工作区收件箱（Inbox）中。

#### 场景二：跨部门重大业务决策评审会（Architecture Decision Record / ADR）
1. **决策提议与评审指派**：在议题中创建 `Decision` 实体，状态初始化为 `proposed`，并指派跨部门负责人为必须参与会签的评审人（Reviewers）。
2. **异步会签评审**：各评审人登录 MeetFlow，在决策详情抽屉中提交审批意见（`approved` / `rejected`）与反馈备注。
3. **定稿与历史替代机制**：当所有人达成共识，组织者执行 `finalize_decision`，决策进入不可变更的 `final` 状态；若未来业务架构升级，可通过 `supersede_decision` 创建新决策并精确关联旧决策形成替代拓扑链条。

## 6. 现有功能强化与架构加固方案

### 6.1 SQLite WAL 并发写入极致调优

SQLite 在 WAL（Write-Ahead Logging）模式下支持多读单写并发。为消除并发阻塞、减少磁盘 I/O 放大，必须对底层 PRAGMA 参数进行全方位深度调优：

```python
# 建议加固方案：backend/app/database.py 中的 SQLite 调优参数
@staticmethod
def _configure_sqlite(connection, _record) -> None:
    cursor = connection.cursor()
    # 1. 基础完整性与并发模式
    cursor.execute("PRAGMA foreign_keys = ON")
    cursor.execute("PRAGMA journal_mode = WAL")
    cursor.execute("PRAGMA busy_timeout = 10000")  # 提升至 10 秒超时退让
    
    # 2. I/O 与性能调优
    cursor.execute("PRAGMA synchronous = NORMAL")   # WAL 模式下保障掉电安全，同时减少 fsync 瓶颈
    cursor.execute("PRAGMA cache_size = -64000")    # 保持 64MB 页面内存缓存
    cursor.execute("PRAGMA temp_store = MEMORY")    # 临时表与中间排序全部置于内存
    cursor.execute("PRAGMA mmap_size = 268435456")  # 启用 256MB 内存映射读取，加速快照查询
    
    # 3. 自动 Checkpoint 优化
    cursor.execute("PRAGMA wal_autocheckpoint = 1000") # 达到 1000 页时自动转储
    cursor.close()
```

此外，针对多协程或后台 Worker 触发的 `sqlite3.OperationalError: database is locked`，需在持久层引入带抖动（Jitter）的指数退让装饰器（Exponential Backoff Retry），彻底消除瞬时冲突。

### 6.2 大附件流式上传与完整性校验机制

当前系统附件上限为 20MB，且无哈希校验。针对团队日常需要上传会议录音、高分辨率架构全景图或演示视频的场景，加固方案如下：

```
                      大附件流式校验与分片存储流水线
  客户端 (Client)                                服务端 (FastAPI Storage)
       │                                                    │
       ├──── 1. POST /api/attachments/init (预检文件名/容量) ──►│ 创建元数据记录
       │◄─── 返回 attachment_id, upload_token, chunk_size ───┤ 状态: pending
       │                                                    │
       ├──── 2. PUT /api/attachments/{id}/chunks/{part} ────►│ 流式分片边写边算
       │    (带 Content-MD5 / 分块索引)                      │ 计算 Part SHA-256
       │                                                    │
       ├──── 3. POST /api/attachments/{id}/complete ────────►│ 组装分片
       │    (提交 Client-Side 总文件 SHA-256)                │ 服务端重算总 SHA-256
       │                                                    │ 验证一致性 ──► 状态: ready
       │◄─── 返回 201 Created (附带 ETag 与安全校验码) ────────┤
```

- **数据层扩展**：在 `attachments` 表新增 `sha256 VARCHAR(64)`、`etag VARCHAR(64)`、`status VARCHAR(16)` 字段（通过 Alembic 迁移交付）。
- **完整性双向校验**：服务端流式接收时，使用 Python `hashlib.sha256()` 边读取边递增更新散列值；落盘后与客户端声明的散列值严格比对，不匹配立即中断并清理脏数据。
- **文件安全嗅探增强**：集成基于文件头特征码的严格 MIME 校验，严禁上传带有可执行属性的文件（`.sh`, `.exe`, `.bat`, `.py`, `.js` 等），防范文件上传穿透漏洞。

### 6.3 鉴权与会话管理安全性升级

- **滑动窗口防暴力破解（Rate Limiting）**：
  在 `/api/auth/login` 入口实现内存级滑动窗口算法（基于 `time.monotonic()` 队列），限制同一 IP 1 分钟内最多尝试 5 次，同一用户名 15 分钟内最多失败 5 次。超限返回 `429 Too Many Requests` 并锁定 15 分钟。
- **会话滑动过期（Sliding Expiration）**：
  现有会话为固定 7 天生命周期。升级为“活跃期滑动延长”机制：当用户在会话后半段发生正常请求时，由后端在响应头刷新 Set-Cookie，延长会话周期；同时保留最大绝对生命周期（如 30 天强制重登）。
- **统一审计日志（Audit Logging）**：
  创建专用的 `security_audit_logs` 表，不可篡改地记录：管理员创建用户、用户密码重置、项目归属转让、插件凭证变更、会议永久删除等敏感动作，记录项包含时间戳、操作人 ID、客户端 IP、操作类型及变更前后指纹。

- **适配自建推理引擎**：原生兼容局域网内由 **Ollama**、**LocalAI** 或 **vLLM** 运行的轻量开源模型（如 `Qwen2.5-7B-Instruct` 或 `Llama-3.1-8B-Instruct`）。

                                                                              │

#### 2. 事件驱动出站 Webhook（Outgoing Webhooks Engine）
- **触发机制**：基于 `plugin_events` 机制，在会议生命周期流转（如会议开始、会议结束生成快照、决策定稿）时对外派发。
- **模板化卡片推送**：
  内置飞书互动卡片（Feishu Card）、钉钉群机器人、企业微信应用机器人以及 Slack Block Kit 模板。
  - **飞书/钉钉卡片效果**：会议结束时，自动在项目绑定的大群推送卡片，标题展现《[项目名] 架构周会纪要已归档》，正文包含核心决策清单、未完待办 @各责任人，并附带直达内网 MeetFlow 会议详情的快捷按钮。

### 8.3 会议音频实时转写与导入（Local Speech-to-Text Pipeline）

- **技术实现**：
  设计 `audio-transcribe` 扩展模块，后端可选集成高性能嵌入式语音引擎 **Faster-Whisper**（基于 CTranslate2，支持纯 CPU 运行与 NVIDIA GPU 加速）。
- **处理链路**：
  1. 用户上传会议录音（支持 `.mp3`, `.m4a`, `.wav` 等主流格式）；
  2. 后台异步任务执行 VAD（Voice Activity Detection，静音切分）与分段转写；
  3. 转写结果按时间轴分段列出，并支持说话人聚类对齐；
  4. 用户在前端可“一键将转写文本导入当前议题手记”，并交由离线 AI 助手提炼。

### P0 阶段：架构加固与双向状态机破局（0 ~ 1 个月）
- **目标**：彻底修复最严重的体验断层，让系统在会议记录与待办流转中真正可用。
- **关键交付成果**：
  1. **数据库与领域服务升级**：重构 `agendas/service.py` 与 `outcomes/service.py`，支持可逆的 Tag 解析与状态映射，在待办更新时触发手记 AST 局部替换。
  2. **SQLite 生产加固**：在 `database.py` 中注入 `PRAGMA synchronous = NORMAL`、`cache_size`、`mmap_size` 等调优配置，并编写并发读写压力测试。
  3. **UI 沉浸式改造**：重塑 `MeetingWorkspaceView.vue` 与 `AgendaWorkbench.vue`，实现双栏对照与全键盘快捷键。

### P1 阶段：生态联动与离线 AI 萃取（1 ~ 3 个月）
- **目标**：打通企业办公外围生态，引入纯内网隐私安全的大模型提炼能力。
- **关键交付成果**：
  1. **分片上传与哈希体系**：交付带有 SHA-256 完整性校验的大文件分块上传流水线，满足 500MB 音视频附件存储。
  2. **外部推送与日历源**：实现 iCal Webcal 订阅与群机器人卡片推送。

### P2 阶段：智能化与企业级治理（3 ~ 6 个月）
- **目标**：满足高安全、大规模研发组织的企业级合规与多媒体会议资产化诉求。
- **关键交付成果**：
  1. **语音转写模块**：引入 Faster-Whisper 本地转写容器组件。
  2. **企业 SSO 认证体系**：支持对接企业自建 Keycloak、GitLab、Active Directory 等身份源。
  3. **多人实时协同协作**：探索基于 Yjs / CRDT 的轻量级多人光标同步方案，实现同场会议多人分工速记。

## 10. 架构师总结与落地展望

MeetFlow 绝非又一个平庸的 Todo-List 或通用 Markdown 笔记工具。它通过极具前瞻性的**“单容器自托管”**、**“零外部依赖”**设计，直击混合办公时代企业在会议资产沉淀中的核心痛点；通过创新的**“Markdown 原始手记与结构化决议/待办任务双向映射状态机”**，巧妙化解了自由书写心流与严谨数据流转之间的百年矛盾。

本白皮书提出的技术加固、交互重塑与生态扩展路线，在最大化保留 MeetFlow 轻量、优雅基因的前提下，为其注入了应对高并发企业场景的工业级韧性与面向未来的智能化潜能。随着各阶段里程碑的稳步推进，MeetFlow 必将成为开源协同与数字化主权领域极具标杆意义的卓越作品。
