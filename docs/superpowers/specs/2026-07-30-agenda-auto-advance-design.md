# 议题自动开启与推进设计

**日期：** 2026-07-30  
**状态：** 已确认，待实施

## 目标

会议开始后立即开始队列中的第一个待开始议题；会议进行中，打开任一待开始议题即开始该议题。用户不再需要、也不再看到“开始此议题”按钮。完成当前议题后，界面自动切换到并开始其后的第一个待开始议题。

这项变更不把未完成议题伪造为已完成：切换到另一个待开始议题时，先前已开始的议题继续是“已开始、未完成”。因此会议中可以有多个已开始未完成的议题，用户仍可回到任一议题完成其记录。

## 状态与数据契约

不新增持久化字段或数据库迁移。议题继续使用既有 `planned`、`in_progress`、`completed`、`skipped` 和 `canceled` 状态，以及既有 `started_at`、`completed_at` 与 `actual_duration_seconds`。

### 开始会议

`POST /api/meetings/{meeting_id}/start` 在一个事务中：

1. 校验会议版本与可开始状态；
2. 将会议设为 `in_progress` 并记录开始时间；
3. 按队列位置查找第一项 `planned` 议题；若存在，将其设为 `in_progress` 并记录开始时间；
4. 为会议和自动开始的议题分别记录活动事件，再一次提交。

没有议题的会议仍可开始，只是没有自动开启的议题。

### 打开待开始议题

会议进行中，用户从队列打开状态为 `planned` 的议题时，前端调用既有议题开始命令。服务端只开始目标议题；不会更改其他 `in_progress` 议题的状态或结束时间。打开 `in_progress`、`completed`、`skipped` 或 `canceled` 项只切换详情，不产生状态变化。

### 完成并自动推进

新增一个面向界面和未来 CLI 的原子“完成并推进”命令。它在一个事务中：

1. 校验当前议题版本、会议仍可编辑；
2. 完成当前议题并以完成时刻计算真实耗时；
3. 从当前项之后按 `position` 查找第一项 `planned` 议题；若存在，立即开始它；
4. 返回被完成的议题和下一项 ID（无下一项时为 `null`），以便前端准确切换详情；
5. 记录相应活动事件并提交一次。

它不会跳过排在中间的已开始未完成项，也不会改变它们的状态。结束会议仍沿用现有规则：所有未结束议题标记为跳过。

服务实现会抽出可在一个事务内复用的议题状态变更辅助逻辑，供会议开始和“完成并推进”使用，避免一次会议开始后再单独发起第二个请求造成半完成状态。未来 CLI 只调用这些 HTTP 命令，不直接读写 SQLite。

## 工作台交互

- 移除详情底部的“开始此议题”操作与相关测试断言。
- 队列选择由工作台统一处理：会议未开始时仅选择；会议进行中选择待开始项时，等待开始命令成功后刷新会议数据并显示该项。
- 当前进行中项的主要操作仍为“完成议题并进入下一项”。成功后使用命令返回的下一项 ID 选择详情；没有下一项时保留已完成项详情。
- 现有议题详情切换过渡继续使用，自动推进与手动打开使用同一条切换路径。

## 视觉状态

队列按议题状态和当前选择状态表达进度：

- 当前打开且 `in_progress` 的行采用方案 B：柔和、低对比度、缓慢流动的背景渐变，保留清晰边框与进行中编号；
- 其他已开始未完成项保留进行中标识，但不播放动画；
- `completed` 项使用固定、静态的完成背景，绝不继承动画；
- `planned`、`skipped` 与 `canceled` 项维持静态；
- `prefers-reduced-motion: reduce` 时，所有新增的背景动画关闭。

动效只用于显示当前正在查看的进行中议题，不会让多个未完成议题同时闪动，也不会改变文本、计时或按钮可访问性。

## 错误与并发

- 开始、完成和自动推进继续使用现有乐观锁。版本冲突或网络失败时，不乐观改写队列状态或选择，保留当前详情并显示现有错误反馈。
- 自动开始首项及完成后推进都必须是单个数据库事务：提交失败时会议与议题状态都回滚。
- 会议结束、取消、已完成会议和非 `planned` 议题继续拒绝不合法的开始/完成转换。

## 验证

后端领域测试覆盖：开始会议自动开始首项、无议题会议仍可开始、原子完成并推进、没有后续待开始项、已开始未完成项不被自动完成，以及冲突时不留下半完成状态。

前端组件与视图测试覆盖：不再出现“开始此议题”、会议进行中打开待开始项会发起开始、完成后依据返回的下一项自动切换、完成项保留静态类、当前进行中项拥有动画类及减少动态效果 CSS。
