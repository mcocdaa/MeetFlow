# MeetFlow Lite 设计说明

## 1. 产品概述

MeetFlow 是一个轻量级个人会议档案工具，用于集中保存会议记录、关键结论、行动项、图片、小文件和会后补充。

产品的核心对象不是 Markdown 文档，而是一个结构化的“会议包”（Meeting Package）。Markdown 仅用于原始记录、关键结论和会后补充等适合自由书写的区域。

第一版的产品重心为：会议档案 70%，行动项追踪 30%。它面向个人使用、黑客松演示和后续部署到远程服务器的场景。

## 2. 目标与非目标

### 2.1 目标

- 在三小时内完成可演示的端到端工作流。
- 以会议为单位保存结构化信息、Markdown 记录、行动项和附件。
- 支持在会议结束后持续追加进展。
- 支持按标题和项目查找会议。
- 汇总所有会议产生的未完成行动项。
- 使用单个 Python 服务运行，并可通过单个 Docker 容器部署。
- 将运行内存保持在 2 GB 以下；正常空闲状态预计仅占用数十到数百 MB。
- 通过挂载一个数据目录完成数据库和附件的持久化。

### 2.2 第一版不做

- 用户注册、登录、权限和多人协作。
- AI 总结、润色或插件系统。
- 实时协同编辑和版本冲突处理。
- 复杂标签体系、人员通讯录和项目管理。
- 文档全文检索。
- PDF、Office 或代码文件的在线编辑。
- 服务端图片缩略图生成。
- Markdown 导出、图片灯箱和文本附件在线预览，这些仅在核心功能完成后考虑。

## 3. 核心工作流

```text
创建会议
   ↓
填写基本信息并手动记录
   ↓
整理关键结论
   ↓
添加行动项和附件
   ↓
会后持续补充进展
   ↓
从首页检索档案或从待办页追踪行动项
```

演示流程如下：

1. 创建“黑客松产品讨论”会议。
2. 填写项目、类型、时间和参与人。
3. 写入数行 Markdown 原始记录。
4. 整理关键结论。
5. 创建两个行动项。
6. 上传一张白板图片和一个 PDF。
7. 返回首页，通过项目或标题找到会议。
8. 打开待办页，查看来自不同会议的未完成行动项。

## 4. 信息架构与页面

### 4.1 首页

首页按会议时间倒序显示会议卡片，而不是普通文档列表。每张卡片显示：

- 标题、会议时间和项目。
- 会议类型和参与人摘要。
- 关键结论、行动项和附件数量。
- 未完成行动项数量。

首页提供：

- 创建会议入口。
- 按标题和项目进行包含匹配的搜索框。
- 进入全部未完成行动项的入口。

### 4.2 会议详情页

会议详情分为五个清晰区域：

1. **概览**：基本信息、关键结论、待完成行动项和附件摘要。
2. **会议记录**：原始 Markdown 记录和独立保存的关键结论。
3. **行动项**：行动内容、负责人、截止日期和状态。
4. **附件**：图片缩略展示，以及普通文件的上传、下载和删除。
5. **后续补充**：按创建时间追加 Markdown 记录。

详情页支持编辑会议基本信息和删除会议。删除完整会议前必须二次确认。

### 4.3 待办页

待办页汇总所有会议中尚未完成的行动项，并显示来源会议、负责人和截止日期。用户可直接更新状态或进入来源会议。

## 5. 技术架构

MeetFlow 采用单体轻量架构：

- **前端**：Vue 3 + Vite，使用原生 CSS，不引入大型 UI 组件库。
- **后端**：FastAPI，由单个 Uvicorn 进程运行。
- **数据库**：SQLite 单文件，不运行独立数据库服务。
- **附件存储**：本地文件系统，数据库仅保存元数据和相对路径。
- **生产部署**：前端构建为静态文件后由 FastAPI 提供，生产环境不运行 Node.js 服务。
- **容器化**：一个 Docker 镜像、一个容器、一个持久化数据目录。

```text
Browser
   ↓
Vue 单页应用
   ↓ /api
FastAPI / Uvicorn
   ├── SQLite：会议及关联数据
   └── data/uploads/：图片和小文件
```

后端保持与 KnowFlow、HarvestFlow、AutoFlow 相似的清晰职责划分，但第一版不复制插件加载器、Redux、MongoDB 或复杂配置系统。后续 AI 功能可通过独立的 `/api/ai/...` 路由和服务模块接入，无需提前建立通用插件框架。

## 6. 模块边界

### 6.1 前端

- `meetings`：会议列表、详情、创建、编辑和删除。
- `actions`：会议内行动项编辑及跨会议汇总。
- `attachments`：上传、下载、删除和图片展示。
- `updates`：会后补充记录。
- `api`：HTTP 请求、响应解析和统一错误处理。

### 6.2 后端

- `api`：请求校验、HTTP 状态码和响应模型。
- `services`：会议删除、附件上传等跨资源业务流程。
- `repositories`：SQLite 数据读写，不包含 HTTP 或文件展示逻辑。
- `storage`：附件路径生成、写入、读取和删除。
- `config`：数据目录、上传大小和服务配置。

每个模块仅依赖下层的明确接口。API 路由不直接拼接磁盘路径，数据库仓库不负责删除文件。

## 7. 数据模型

### 7.1 meetings

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | TEXT | UUID 主键 |
| title | TEXT | 必填会议标题 |
| project | TEXT | 可选项目名称 |
| meeting_type | TEXT | 可选会议类型 |
| meeting_date | DATETIME | 必填会议时间 |
| participants | TEXT | JSON 字符串数组 |
| raw_notes_markdown | TEXT | 原始会议记录 |
| conclusions_markdown | TEXT | 关键结论 |
| created_at | DATETIME | 创建时间 |
| updated_at | DATETIME | 最后更新时间 |

第一版不建立人员表、项目表和会议类型表。项目及类型使用普通文本，前端可以从历史会议中提取已有值作为输入建议。

### 7.2 action_items

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | TEXT | UUID 主键 |
| meeting_id | TEXT | 所属会议外键 |
| content | TEXT | 必填行动内容 |
| owner | TEXT | 可选负责人 |
| due_date | DATE | 可选截止日期 |
| status | TEXT | `open` 或 `done` |
| created_at | DATETIME | 创建时间 |
| updated_at | DATETIME | 最后更新时间 |

### 7.3 attachments

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | TEXT | UUID 主键 |
| meeting_id | TEXT | 所属会议外键 |
| original_name | TEXT | 用户上传时的文件名 |
| stored_name | TEXT | UUID 生成的磁盘文件名 |
| mime_type | TEXT | 服务端根据文件内容或安全回退规则确定的 MIME 类型 |
| size | INTEGER | 文件字节数 |
| attachment_type | TEXT | `image` 或 `file` |
| created_at | DATETIME | 上传时间 |

### 7.4 meeting_updates

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | TEXT | UUID 主键 |
| meeting_id | TEXT | 所属会议外键 |
| content_markdown | TEXT | 必填补充内容 |
| created_at | DATETIME | 创建时间 |

所有子表通过外键关联会议，并启用 SQLite 外键约束。删除会议时，数据库记录使用级联删除；附件磁盘清理由会议服务负责。

## 8. 文件存储

本地测试和远程 Docker 使用相同布局：

```text
data/
├── meetflow.db
└── uploads/
    └── <meeting-id>/
        └── <uuid>.<ext>
```

文件规则如下：

- 单个文件最大 20 MB。
- 第一版接受图片和普通小文件，不维护复杂扩展名白名单。只有 JPEG、PNG、GIF 和 WebP 可作为图片内联展示；SVG、HTML、脚本及其他文件始终作为下载附件返回，不能作为可执行内容提供。
- 磁盘文件名使用服务端 UUID，原文件名仅用于展示和下载响应。
- 存储路径必须由服务端生成，并验证最终路径位于该会议目录内，防止路径穿越。
- 图片由浏览器通过受控附件接口加载，并使用 CSS 生成视觉缩略图，不创建额外缩略图文件。
- 上传时先写入临时文件，完成大小校验后原子移动到目标位置，再写入数据库记录。
- 若数据库写入失败，删除已移动的文件。
- 删除附件时先确认归属，删除数据库记录后再删除磁盘文件；磁盘文件不存在时仍将数据库删除视为成功并记录警告。
- 删除会议时，数据库事务完成后清理对应附件目录；清理失败需记录错误，但不恢复已经删除的会议数据。

## 9. API 设计

所有业务接口以 `/api` 为前缀并返回 JSON；文件下载接口返回流式响应。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/health` | 健康检查 |
| GET | `/api/meetings` | 会议列表及标题/项目搜索 |
| POST | `/api/meetings` | 创建会议 |
| GET | `/api/meetings/{id}` | 获取完整会议包 |
| PUT | `/api/meetings/{id}` | 更新会议基本信息和记录 |
| DELETE | `/api/meetings/{id}` | 删除会议及关联数据 |
| POST | `/api/meetings/{id}/actions` | 创建行动项 |
| PUT | `/api/meetings/{id}/actions/{action_id}` | 更新行动项 |
| DELETE | `/api/meetings/{id}/actions/{action_id}` | 删除行动项 |
| GET | `/api/actions?status=open` | 跨会议查询行动项 |
| POST | `/api/meetings/{id}/attachments` | 上传一个附件 |
| GET | `/api/meetings/{id}/attachments/{attachment_id}` | 下载或展示附件 |
| DELETE | `/api/meetings/{id}/attachments/{attachment_id}` | 删除附件 |
| POST | `/api/meetings/{id}/updates` | 添加会后补充 |
| DELETE | `/api/meetings/{id}/updates/{update_id}` | 删除会后补充 |

会议详情接口一次返回会议、行动项、附件元数据和补充记录，减少前端的组装请求。Markdown 始终以原文存储和传输，由前端进行安全渲染。

## 10. 错误处理与安全边界

后端统一使用以下错误结构：

```json
{
  "error": {
    "code": "attachment_too_large",
    "message": "单个附件不能超过 20 MB"
  }
}
```

- 缺少标题、会议时间或行动内容时返回 422，并指出具体字段。
- 资源不存在或子资源不属于指定会议时返回 404。
- 文件超限返回 413。
- 数据库或磁盘故障返回 500，响应中不泄露路径、SQL 或堆栈。
- 前端提交失败时保留未提交内容，并显示可重试提示。
- Markdown 渲染必须禁用或清理原始 HTML，避免存储型 XSS。
- 下载响应设置安全的 `Content-Disposition`，普通文件不以内联 HTML 执行。
- 第一版没有应用内认证。远程部署必须置于可信内网、VPN 或带认证的反向代理之后；不得直接无保护暴露到公网。

## 11. Docker 与远程部署

生产镜像采用多阶段构建：Node 阶段构建 Vue 静态资源，Python 阶段安装后端依赖并复制前端产物。运行时只有 Python 和应用文件。

容器约定：

- FastAPI 监听 `0.0.0.0:8000`。
- `/app/data` 为唯一必须持久化的目录。
- 启动时自动创建数据库、表和上传目录。
- 提供 `/api/health` 供 Docker 或反向代理进行健康检查。
- SQLite 使用 WAL 模式和合理的 busy timeout，以适应个人工具的低并发读写。
- 单进程 Uvicorn，避免多个进程同时执行初始化和本地文件操作。

本地开发可分别运行 Vite 和 FastAPI以支持热更新；部署构建必须验证由 FastAPI 正确返回前端路由和静态资源。

## 12. 测试与验收

### 12.1 自动化测试重点

- 会议创建、读取、更新、删除及标题/项目搜索。
- 会议详情能完整返回行动项、附件元数据和补充记录。
- 行动项创建、编辑、删除和跨会议状态筛选。
- 合法附件上传、下载和删除。
- 超过 20 MB 的附件被拒绝，且不残留文件或数据库记录。
- 删除会议会级联删除子记录并清理附件目录。
- 不存在及归属错误的资源返回 404。
- Markdown 渲染不执行危险 HTML。
- 健康检查和构建后的前端入口可访问。

### 12.2 Docker 验收

1. 成功构建单个镜像并启动一个容器。
2. 创建包含行动项和附件的会议。
3. 停止并重新创建容器。
4. 使用同一 `/app/data` 挂载后，会议和附件仍然存在且可访问。
5. 在受限为 2 GB 内存的环境中完成核心演示流程。

## 13. 三小时实施优先级

1. 会议 CRUD、SQLite 初始化和首页。
2. 会议详情、原始记录与关键结论。
3. 行动项及待办汇总。
4. 图片和小文件附件。
5. 标题/项目搜索和界面完善。
6. Docker 单容器构建及持久化验证。

若时间不足，按顺序舍弃：文本文件在线预览、图片灯箱、后续补充、复杂视觉效果。会议、关键结论、行动项、附件和单容器部署构成不可拆分的演示闭环。

## 14. 后续扩展方向

核心模型稳定后可以独立增加：

- AI 润色原始记录或生成关键结论、行动项。
- 将完整会议包导出为 Markdown 或压缩包。
- 文本附件预览和图片灯箱。
- 项目、参与人和会议类型的独立管理。
- 应用内认证和多人权限。

这些扩展必须通过独立服务或模块接入，不能改变第一版会议包、行动项和附件的核心边界。
