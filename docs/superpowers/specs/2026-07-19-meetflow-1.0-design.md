# MeetFlow 1.0 Design

**Date:** 2026-07-19  
**Status:** Approved design  
**Baseline:** `v0.1.0` at commit `0613cb7`  
**Deployment constraint:** One Docker container, one Uvicorn process, SQLite, local attachment storage

## 1. Product definition

MeetFlow 1.0 is a lightweight shared workspace that turns meetings into traceable project progress. It organizes preparation, discussion, decisions, actions, open questions, files, comments, and follow-up without becoming a general-purpose document editor or a full project-management suite.

The central workflow is:

```text
Project context
  → meeting series and preparation
  → mutable agenda
  → discussion by agenda item
  → decisions, actions, and open questions
  → completed meeting snapshot
  → project history and next meeting
```

The product remains suitable for a small team and a server with less than 2 GB of memory.

## 2. Goals

MeetFlow 1.0 must provide:

- Real project entities rather than project-name strings.
- Recurring meeting series and standalone meetings.
- A mutable, structured agenda that can change during a meeting.
- A traceable chain from each agenda item to its decisions, actions, and open questions.
- A trustworthy completed-meeting snapshot with amendments and explicit reopening.
- A personal attention-first home page.
- Project overview, decision log, action tracking, files, and activity history.
- Comments, mentions, assignments, an in-app inbox, and incremental browser polling.
- Markdown-first WYSIWYG editing.
- Fixed, administrator-installed trusted Python plugins with independent configuration.
- Persistent, deduplicated background jobs for simple AI text generation.
- A single-container deployment with backup and restore support.

## 3. Non-goals

MeetFlow 1.0 will not provide:

- Compatibility or automatic data migration from the v0.1 schema.
- A generic Notion-style block editor.
- Real-time Y.js collaborative document editing.
- Email, Slack, Teams, enterprise WeChat, or other external notifications in core.
- Agent loops, ToolCall, autonomous web research, browser automation, or a platform tool registry.
- Plugin code upload, installation, deletion, or editing from the web UI.
- A security sandbox for trusted Python plugin code.
- Redis, Celery, PostgreSQL, or a second runtime container.
- Per-project private access control; the workspace remains shared by all approved members.

## 4. Research findings

The redesign follows several patterns found in established tools:

- Recurring meeting systems carry agendas and unfinished work across occurrences instead of treating every meeting as an unrelated document. [Decisions recurring meetings](https://support.meetingdecisions.com/en/recurring-meetings) and [standing agendas](https://support.meetingdecisions.com/en/create-standing-agendas-for-meeting-series-recurring-meetings) illustrate this pattern.
- Effective meeting records separate agenda topics, discussion, decisions, and owned actions. [Confluence meeting notes](https://www.atlassian.com/software/confluence/templates/meeting-notes) and its [weekly meeting notes](https://www.atlassian.com/software/confluence/templates/weekly-meeting-notes) use this structure.
- Decisions become substantially more useful when promoted out of prose into a searchable project-level log. [Decisions decision logging](https://support.meetingdecisions.com/en/logging-a-new-decision) and Microsoft's [engineering decision log](https://microsoft.github.io/code-with-engineering-playbook/design/design-reviews/decision-log/doc/decision-log/) use this model.
- Project pages work best as stable context surfaces containing status, owner, resources, recent updates, and upcoming work rather than as chart-heavy dashboards. [Linear project overview](https://linear.app/docs/project-overview) and [project updates](https://linear.app/docs/initiative-and-project-updates) follow this pattern.
- Markdown-first WYSIWYG editing can preserve portable storage without displaying raw source and preview side-by-side. [Milkdown](https://milkdown.dev/) is a headless, plugin-driven WYSIWYG Markdown framework built on ProseMirror and Remark.

## 5. Design principles

### 5.1 Structured facts, flexible prose

Projects, meetings, agendas, decisions, actions, people, and statuses are structured records. Discussion notes, project updates, amendments, comments, and AI results use Markdown.

### 5.2 Attention, not activity volume

The home page answers “what needs my attention?” It does not display a marketing hero, a raw announcement ticker, or an unfiltered event feed.

### 5.3 Project context, meeting occurrence

Projects hold long-term context. Meeting series hold cadence and standing preparation. A meeting records one occurrence. Agenda items organize the work inside that occurrence.

### 5.4 Outcomes remain traceable

Every decision, action, and open question created during a meeting retains its agenda-item and meeting source. Records cannot be deleted in ways that silently break this chain.

### 5.5 Formal completion is trustworthy

Finishing a meeting creates a stable snapshot. Later correction happens through an amendment or an explicit reopen operation, both of which remain visible in history.

### 5.6 Plugins are honest about trust

An installed Python plugin is fully trusted code. MeetFlow displays its origin, version, declared actions, and runtime state but does not claim to sandbox it.

### 5.7 AI produces drafts

AI output is an editable artifact. It never becomes official project or meeting data until a user applies it through an ordinary domain API.

## 6. System architecture

MeetFlow remains a modular monolith:

```text
Vue SPA
  ↓ same-origin JSON API
FastAPI
  ├── auth
  ├── projects
  ├── meetings
  ├── outcomes
  ├── collaboration
  ├── inbox
  ├── plugins
  ├── jobs
  └── attachments
  ↓
SQLite + /app/data/uploads
```

The production image uses a Node build stage for Vue and a Python runtime stage for FastAPI. FastAPI serves both `/api/*` and the built SPA. Uvicorn runs one worker.

SQLite uses foreign keys, WAL mode, a busy timeout, and explicit transactions for state transitions. Alembic owns schema versions from a new 1.0 baseline.

The existing v0.1 database is not migrated. Startup must not silently delete it. Deployment documentation instructs the administrator to archive the old `data/` directory and start with a new directory.

The product has one shared workspace. Approved active members can read all projects and meetings. Administrative APIs remain role-restricted.

Occurrences are created explicitly from the series page through “Create next meeting.” MeetFlow does not run a scheduler that automatically creates future meetings.

### 7.5 Agenda items

```text
agenda_items
- id
- meeting_id
- title
- agenda_type: information | discussion | decision
- proposer_user_id
- presenter_user_id
- estimated_minutes
- notes_markdown
- status: planned | in_progress | completed | skipped | canceled
- position
- carry_from_open_question_id nullable
- version
- created_at
- updated_at
- started_at
- completed_at
```

Agenda items form a mutable queue throughout preparation and the active meeting. Members can insert items at any position, reorder them, edit them, skip them, cancel them, or move them to another meeting.

Deletion rules:

- An agenda item with no linked outcomes, comments, or attachments can be deleted.
- An agenda item with linked outcomes cannot be hard-deleted.
- Such an item may be canceled, or its outcomes may first be explicitly migrated to another agenda item.
- A skipped item may be converted into an open question or copied into a later meeting.

Decisions and actions may also be created directly from a project page. Meeting-origin records always retain their source links.

An amendment adds context without mutating the completed snapshot. Reopening a meeting is a separate audited state transition.

### 7.8 Files and comments

Attachments can belong to a project, meeting, or agenda item. They may be added at any point, including after meeting completion.

```text

```

Application services validate polymorphic targets before inserting a record. Deleted comments remain as tombstones so replies do not lose context.

## 8. Meeting lifecycle

### 8.1 Preparation

Members create or copy agenda items, attach materials, suggest topics, assign presenters, estimate time, and resolve open questions carried from earlier meetings.

The meeting moves from `draft` to `ready` when required metadata is present. This is a reversible transition.

### 8.2 In progress

Starting a meeting changes its status to `in_progress` and records `started_at`.

The current agenda item is displayed in the main pane. The queue stays in a narrow right sidebar. It can be reordered or extended at any time.

The main pane groups actions by intent:

- Outcome actions near the outcome area: add decision, add action, add open question.
- Agenda-flow actions in a separate bottom-right group: skip/move to next meeting, complete and advance.
- Whole-meeting action in the page header: finish meeting.

The finish-meeting button is visually weak while unresolved agenda items remain. Attempting to finish returns a structured validation error listing those items.

### 8.3 Completion

Finishing a meeting runs in one database transaction:

1. Validate every agenda item has a terminal state.
2. Create an immutable `meeting_snapshots` row containing the final agenda order and relevant meeting fields.
3. Verify every outcome retains a valid source.
4. Set the meeting to `completed` and record `completed_at`.
5. Write activity events and direct-user notifications.

The completed page shows the meeting summary and an ordered chain:

```text
agenda item
  → discussion notes and materials
  → decisions, actions, and open questions
  → future destination or resolution
```

### 8.4 After completion

- Members can add comments and attachments.
- Members cannot directly change the final agenda or completed notes.
- “Add amendment” creates an append-only correction with author, time, and reason.
- “Reopen meeting” changes the meeting back to `in_progress`, increments its version, and writes an explicit audit event.
- Completing a reopened meeting creates a new numbered snapshot, updates `current_snapshot_id`, and keeps earlier snapshots plus the reopen/completion history visible.

## 9. Information architecture

The authenticated application shell uses a stable sidebar:

```text
For you
Projects
Meetings
Actions
Decisions
Inbox
AI tasks

Workspace
  Members
  Plugins (admin)
  Settings (admin)
```

The current marketing-style hero is removed from the signed-in home page.

### 9.1 “For you” home

The default home page is a personal priority queue. It presents:

1. Overdue actions assigned to the user.
2. Decisions awaiting the user's confirmation.
3. Meetings the user must prepare, host, record, or present.
4. Actions approaching their due date.
5. Unread mentions and replies.
6. Important changes from projects the user participates in.
7. Completed AI text-generation results.

The same underlying object appears once. Reasons are combined on the card, such as “overdue · one new reply.”

Upcoming meetings and an optional on-demand AI brief appear in a narrower secondary column. The AI brief is never an automatic scrolling announcement.

### 9.2 Project page

The project page is a long-term context surface, not a statistics dashboard.

Header properties include status, health, lead, members, and target date. Tabs are:

```text
Overview | Meetings | Decisions | Actions | Files | Activity
```

Overview prioritizes:

- Latest confirmed project update or editable AI draft.
- Items requiring attention.
- Next meeting and meeting series.
- Recent decisions.
- Compact counts for meetings, open actions, and decisions.

### 9.3 Meeting page

The meeting page changes by lifecycle stage:

- Preparation: agenda building, materials, participant roles, and carried work.
- In progress: wide agenda-detail pane on the left and a narrow mutable queue on the right.
- Completed: final minutes, outcome tabs, amendments, files, comments, and the complete agenda chain.

The right queue is approximately 25–30% of the workspace width. The left pane owns the primary reading and editing experience.

### 9.4 WYSIWYG Markdown

Milkdown replaces raw textarea/preview pairs for long-form Markdown.

MeetFlow stores Markdown, sanitizes rendered output, and exposes Markdown export. The editor receives MeetFlow styling rather than a generic document-editor theme.

The editor supports headings, bold, lists, links, mentions, and attachment references. It is not a generic block database.

## 10. Optimistic concurrency

Editable entities include an integer `version`. Mutation requests send `expected_version`.

If the server version differs, the API returns `409 version_conflict` with the latest server representation. The frontend retains the local draft and offers:

- Copy local draft.
- Compare with the server value.
- Reload the server value.
- Deliberately overwrite through a new request using the latest expected version.

Comments and independent outcomes can be created concurrently because they do not rewrite the parent document.

MeetFlow 1.0 does not use Y.js or claim live collaborative document editing.

## 11. Activity, inbox, and comments

### 11.1 Activity events

Important domain operations append lightweight events in the same database transaction as the business change.

```text
activity_events
- id
- actor_user_id
- project_id nullable
- event_type
- subject_type
- subject_id
- metadata_json
- created_at
```

Examples include project status changes, meeting lifecycle changes, agenda reordering, decision finalization, action assignment/completion, file upload, and AI artifact application.

Activity is not event sourcing. Domain tables remain the source of truth. UI activity feeds group repetitive edits performed close together.

### 11.2 Notifications

Only directly relevant events create notifications:

- Mention or comment reply.
- Action assignment, approaching due date, or overdue state.
- Host, recorder, or presenter assignment.
- Decision confirmation request.
- Participating meeting cancellation, rescheduling, or reopening.
- The user's AI task success or failure.

Generic edits and unrelated uploads remain activity events without notifying all members.

```text
notifications
- id
- user_id
- event_id nullable
- notification_type
- subject_type
- subject_id
- title
- body
- dedupe_key nullable
- read_at nullable
- archived_at nullable
- created_at
```

External notification channels are outside core and may be added later by trusted plugins.

Time-based action notifications are created idempotently when the affected user's inbox or attention endpoint is queried. Their deduplication key prevents repeated “due soon” or “overdue” notifications for the same action and threshold. Core does not require a separate scheduler for these notifications.

### 11.3 Incremental polling

The Vue application requests incremental inbox changes every 20–30 seconds:

```http
GET /api/inbox/changes?cursor=<last_event_id>
```

The response includes `next_cursor`, unread count, new notifications, and changed attention identifiers.

Polling slows or pauses in a hidden tab, refreshes immediately when the tab regains focus, uses jitter between clients, and exponentially backs off on failure.

An open AI-task detail may poll every 2–5 seconds until reaching a terminal state.

## 12. Plugins

### 12.1 Trust and installation

Plugin code is trusted Python installed by the server administrator. `/app/plugins` remains read-only while the container is running.

The web UI cannot upload, install, modify, or delete plugin files. Installing or changing code requires changing host files or building a new image, then restarting the container.

The plugin page displays:

- Plugin name, ID, version, source path, and load error.
- Declared text actions and target scopes.
- Actual runtime state.
- Desired enable state.
- An explicit full-trust warning.

Plugins appear as compact list rows. Clicking a row expands its independent configuration form.

### 12.2 Independent configuration

Every plugin owns its API base URL, API key, model name, timeout, and additional schema-defined fields. There is no global AI provider.

```text
plugin_states
- plugin_id
- desired_enabled
- config_revision
- updated_by
- updated_at

plugin_configs
- plugin_id
- config_key
- stored_value
- is_secret
- updated_at
```

Actual loaded descriptors and runtime state live in process memory and are rebuilt only at application startup. Desired state and configuration remain in SQLite.

Secrets are encrypted using a key derived from `APP_SECRET_KEY`, never returned to the browser, and never written to logs.

Configuration changes affect the next submitted task and increment `config_revision`. Code is never hot-reloaded.

Enable/disable buttons modify desired state. Actual Python loading and unloading only occurs on container startup. The UI therefore shows states such as:

- Running.
- Disabled.
- Enable after restart.
- Disable after restart.
- Load failed.

### 12.3 Supported AI scope

MeetFlow core supports ordinary text-generation actions:

- Meeting minutes: meeting context to Markdown minutes draft.
- Project brief: project meetings, decisions, actions, and updates to a progress draft.
- Text polish: selected Markdown and instruction to rewritten Markdown.
- Context Q&A: project or meeting text plus a question to a plain text answer.
- Report writing: user-provided project, meeting, and supported text-attachment content to a Markdown report.

Core does not provide ToolCall, web search, autonomous browsing, an agent loop, or a research agent. A trusted Python plugin may independently implement external API calls, but those capabilities belong to that plugin and are not a MeetFlow platform guarantee.

Core context builders may include Markdown fields and explicitly selected previewable text attachments (`.md`, `.txt`, `.json`, `.yaml`, `.yml`, `.log`, and `.py`) subject to a text-size limit. PDF, office documents, images, audio, and other binary files contribute metadata only; core does not extract or OCR their contents.

## 13. Persistent plugin jobs

Every plugin action is submitted as a persistent SQLite job.

```text
plugin_jobs
- id
- plugin_id
- action_id
- target_type
- target_id
- normalized_input_json
- normalized_input_hash
- dedupe_key
- status: queued | requesting | succeeded | failed | interrupted | canceled
- plugin_version
- config_revision
- result_markdown nullable
- result_json nullable
- error_code nullable
- error_message nullable
- created_by
- created_at
- started_at nullable
- finished_at nullable
```

### 13.1 Duplicate prevention

The deduplication key hashes plugin ID, action ID, target, and normalized input. SQLite enforces a partial unique index for jobs in `queued` or `requesting` state.

Submitting the same active job returns the existing job with `200`, not a new job. The frontend also disables the submit button after the first accepted response.

After success or failure, the user can explicitly select “Run again,” which creates a new job.

### 13.2 Worker behavior

One in-process worker claims queued jobs. The database is the queue source of truth; an in-memory event may wake the worker but does not own job state.

Job states remain intentionally simple. MeetFlow does not display invented model-thinking steps or percentages.

On container startup:

- Queued jobs remain queued.
- Jobs left in `requesting` become `interrupted`.
- Interrupted requests are not automatically replayed because the external provider may already have processed them.

Before execution, the worker verifies the plugin is loaded, desired/running state is valid, and `config_revision` still matches. A mismatch produces `config_changed` and requires a new submission.

### 13.3 Results and application

AI Tasks is a normal navigation page showing task, context, submitter, time, status, error, result, and application state.

Results are editable artifacts. Applying a result calls an ordinary version-checked domain endpoint and writes an activity event. Task history records that the result was applied but does not itself mutate a project or meeting.

## 15. Error handling

All errors retain the existing envelope:

```json
{
  "error": {
    "code": "meeting_has_unresolved_agenda",
    "message": "仍有 2 个议题尚未完成或跳过",
    "details": {}
  }
}
```

Required cases include:

- `version_conflict`: another user saved a newer resource version.
- `agenda_has_outcomes`: an agenda item cannot be hard-deleted.
- `meeting_has_unresolved_agenda`: finish validation failed.
- `meeting_locked`: completed content requires amendment or reopen.
- `invalid_state_transition`: requested lifecycle move is not allowed.
- `duplicate_job`: internally resolves to and returns the existing active job.
- `plugin_not_loaded`: configured plugin is not running.
- `plugin_config_changed`: queued job no longer matches configuration.
- `plugin_timeout`, `plugin_failed`, and `plugin_invalid_output`.
- `attachment_too_large`, `attachment_file_missing`, and storage errors.
- `cursor_expired`: inbox client must perform a full unread-state refresh.

Failed plugin jobs never modify official domain data. Error responses and logs do not expose paths, SQL, passwords, plugin secrets, prompts containing private content, or exception stacks.

## 16. Security

- Authentication remains signed HttpOnly cookies with session-version invalidation.
- Production requires HTTPS, secure cookies, strong secrets, and explicit trusted origins.
- State-changing same-origin requests continue to validate `Origin`.
- Markdown rendering and editor output are sanitized.
- Attachments use content-based inline-image detection and safe download headers.
- Plugin configuration secrets remain encrypted and admin-only.
- Plugin code is explicitly trusted and has the same process permissions as MeetFlow.
- `/app/plugins` is mounted read-only.
- Ordinary members can run only actions whose manifests allow their role.
- AI task results and logs are visible only to authenticated workspace members; plugin configuration remains admin-only.

## 18. Internal delivery checkpoints

MeetFlow 1.0 is the product target, but implementation proceeds through independently verifiable checkpoints:

1. New Alembic baseline, users, projects, meeting series, meetings, agendas, and explicit state transitions.
2. New application shell, personal home, project pages, lifecycle-aware meeting workspace, and Milkdown integration.
3. Decisions, actions, open questions, files, comments, activity events, notifications, and polling.
4. Plugin accordion management, independent configuration, desired/runtime state, persistent jobs, deduplication, and simple text-generation actions.
5. Conflict UX, accessibility, export, backup/restore, Docker validation, performance checks, and complete documentation.

Each checkpoint must keep its implemented scope tested and runnable. The final release is tagged only after the complete 1.0 acceptance suite passes.
