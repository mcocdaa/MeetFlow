# Public Container Release and Direct Docker Run Design

## Goal

Make every validated semantic-version Git tag publish a public MeetFlow image
that starts directly with `docker run` on both x86-64 and ARM64 Linux servers.
The normal deployment path must keep its runtime data in the operator's current
directory and put its required settings on the `docker run` command line.

## Scope and non-goals

This work extends the existing Docker image, public GHCR package, and tag
workflow. It does not change MeetFlow's application features, database schema,
authentication model, or plugin API. It does not create a hosted service,
automatically provision a domain or TLS certificate, or push a release tag.

## Image and release contract

The published image remains `ghcr.io/mcocdaa/meetflow` and remains public. A
successful push of a Git tag in this exact form triggers the release workflow:

```
v<major>.<minor>.<patch>
v<major>.<minor>.<patch>-<pre-release>
```

The workflow rejects any other `v*` tag before a container is pushed. It first
runs the existing backend tests and frontend test/build gates. It then uses
Buildx with QEMU to publish one manifest list containing both
`linux/amd64` and `linux/arm64` images.

For a stable `v1.4.2` tag, the public image receives all of these tags:

- `v1.4.2`, matching the Git tag exactly;
- `1.4.2`, the immutable semantic version;
- `1.4`, the mutable minor-release channel;
- the immutable source SHA tag generated by Docker metadata; and
- `latest`, the current stable-release channel.

A pre-release such as `v1.4.2-rc.1` receives its exact Git and semantic
version tags, but never updates `latest` or the `1.4` channel. This makes a
specific version suitable for rollback while keeping the convenience tags
predictable.

OCI labels, BuildKit cache, provenance, and an SBOM are published where the
selected Docker actions support them. The workflow retains least-privilege
`contents: read` and `packages: write` permissions; it authenticates to GHCR
only with the workflow's `GITHUB_TOKEN`.

## Runtime image contract

The image supplies the production-invariant application paths itself:

- database URL: `sqlite:////app/data/meetflow.db`;
- data directory: `/app/data`;
- plugin directory: `/app/plugins`; and
- frontend assets: `/app/frontend-dist`.

These defaults let the published image run without copying source files or
setting internal paths by hand. Operators may still override an advanced
setting deliberately through Docker environment variables.

The container stays single-process, read-only except for its data mount and
temporary filesystem, runs with `init: true`, forbids new privileges, exposes
port 8000, has a health check against `/api/health`, and restarts unless
stopped. These are the same operational protections already used by Compose.

## Normal direct-run deployment

The normal path is intentionally a command-line configuration path, not an
env-file path. From an empty deployment directory, the operator starts one
logical `docker run` command like this (replace every marked value):

```bash
docker run -d --name meetflow --init --read-only --tmpfs /tmp:size=64m \
  --security-opt no-new-privileges:true --restart unless-stopped \
  -p 127.0.0.1:8000:8000 \
  -v "$PWD/data:/app/data" \
  -e APP_ENV=production \
  -e ADMIN_USERNAME=admin \
  -e ADMIN_PASSWORD='replace-with-a-strong-password' \
  -e APP_SECRET_KEY='replace-with-a-persistent-random-secret-of-at-least-32-characters' \
  -e ALLOW_REGISTRATION=false \
  -e SECURE_COOKIES=true \
  -e TRUSTED_ORIGINS=https://meetflow.example.com \
  ghcr.io/mcocdaa/meetflow:v1.4.2
```

`$PWD/data` is a bind mount, so the host database and uploads are stored in
`./data/` next to the deployment command rather than in Docker's opaque named
volume store. `/app/data` remains the fixed path inside the container. Docker
creates the host directory for `-v` when necessary; the documentation also
shows `mkdir -p data` as an optional explicit preparation step.

The default host binding is loopback-only. A Caddy or Nginx reverse proxy
terminates HTTPS and forwards to `127.0.0.1:8000`. Production settings reject
an HTTP trusted origin or disabled secure cookies. Direct `0.0.0.0` HTTP is
documented only as a restricted trusted-LAN/development scenario, never as a
public production recipe.

`APP_SECRET_KEY` is persistent state: it must be recorded in the operator's
secret manager and supplied unchanged after an image update. Changing it
invalidates sessions and prevents existing encrypted plugin settings from
being decrypted. The bootstrap administrator password only creates the first
administrator; it does not reset an existing account on later starts.

Inline `-e` values satisfy the requested default, but they can be retained in
shell history and are visible to Docker administrators through inspection.
The deployment documentation calls this out before showing real values.

## Advanced environment-file configuration

No new configuration template is introduced. The repository's existing
`.env.example` remains the one template, including the local-development
defaults most recently refined by the project. An operator who needs a
persisted configuration file can copy and edit it:

```bash
cp .env.example .env
```

For that advanced path, the operator changes the production-required values
in `.env` and replaces the individual `-e` settings with:

```bash
--env-file ./.env
```

Docker command-line `-e` values take precedence over the advanced file, so an
operator can override one setting temporarily without editing the file. The
documentation explicitly keeps `.env`, `data/`, backups, and GHCR credentials
out of Git.

## Plugins, update, backup, and rollback

No custom plugin mount is necessary for the built-in image content. An
operator adding trusted custom plugins may append a read-only bind mount such
as `-v "$PWD/plugins:/app/plugins:ro"`; that directory then owns the entire
plugin tree exposed to the application and must contain its registry file.

The documentation uses exact version tags for an update and rollback. It
requires a backup before replacing the container and instructs the operator to
reuse the same `./data/` directory and persistent application secret. The
existing SQLite-safe container backup helper remains the preferred backup
mechanism. `latest` is a convenience channel, not a rollback target.

## Documentation changes

README becomes the public operator entry point and will contain:

1. the image name, public availability, supported platforms, and tag policy;
2. the normal single-command `docker run` launch sequence using command-line
   variables and `./data/`;
3. one-time secret generation and HTTPS reverse-proxy prerequisites;
4. advanced `.env.example` to `.env` configuration only when needed;
5. optional plugin mounting, health checks, updates, rollback, and backups;
6. a concise explanation that no GitHub login is needed to pull the public
   image.

The existing Compose route remains documented for source checkout users, but
it is no longer the primary server-installation path.

## Failure handling

- Invalid tag: the workflow stops before login/build/push and reports the
  required SemVer shape.
- Test or frontend-build failure: no release image is pushed.
- Multi-architecture build/push failure: the workflow fails rather than
  advancing `latest`; operators retain the last known-good tag.
- Production configuration failure: Settings reports the invalid password,
  secret, secure-cookie, or trusted-origin condition at startup.
- Unhealthy container: Docker restarts it under the existing restart policy;
  the operator checks `docker logs meetflow` and `/api/health` through the
  local binding or proxy.
- Data or secret loss: recovery requires the same `./data/` backup and the
  original `APP_SECRET_KEY`; the README makes this dependency explicit.

## Verification

The implementation verifies the release path proportionally to what can be
proved locally:

1. retain the existing backend tests, frontend tests, and production frontend
   build;
2. add a CI container smoke step that starts the built image with the same
   production environment contract and waits for its health check;
3. build the image locally and inspect the image defaults, then run the direct
   bind-mount `docker run` command against a temporary `./data/` directory;
4. validate workflow YAML and inspect the generated release tags/configuration
   statically; and
5. run the release workflow only by pushing a future approved Git tag. Local
   verification cannot claim that GHCR has received an image.

Multi-architecture manifest publication itself is verified by GitHub Actions,
because the local environment need not emulate or run both target platforms.
