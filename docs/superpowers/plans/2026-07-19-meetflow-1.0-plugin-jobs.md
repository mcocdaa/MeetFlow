# MeetFlow 1.0 Plugin Jobs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn fixed, trusted plugins into restart-aware background text tasks with admin-only configuration, active-job deduplication, persistent history, and editable results.

**Architecture:** Plugin code remains read-only and is discovered only at process startup. The database stores desired enabled state and per-plugin configuration, while the registry reports actual runtime state. All actions submit persistent `PluginJob` rows to one in-process worker. Handlers receive serialized MeetFlow context and return text suggestions only—no agents, tool calls, web research, or direct domain writes.

**Tech Stack:** FastAPI, SQLAlchemy 2, SQLite, Pydantic 2, asyncio, httpx, pytest, Vue 3, TypeScript, Vitest

- [ ] **Step 3: Define manifest and runtime contracts**

```python
class PluginManifest(BaseModel):
    id: str = Field(pattern=r"^[a-z0-9][a-z0-9-]{1,63}$")
    name: str
    version: str
    entrypoint: str = "backend:plugin"
    actions: list[PluginAction]
    config_schema: dict[str, Any]

class PluginAction(BaseModel):
    id: str
    label: str
    context_types: list[Literal["project", "meeting"]]
```

Discovery rejects symlinks escaping the plugins root, duplicate IDs, invalid manifests, and non-callable entrypoints. It imports only at startup. There is no upload/install/reload endpoint.

- [ ] **Step 4: Separate desired and runtime state**

Persist `PluginState(plugin_id, desired_enabled, config_revision, updated_at, updated_by)` and individual `PluginConfig(plugin_id, config_key, stored_value, is_secret, updated_at)` rows. Encrypt secret values with an authenticated key derived from `APP_SECRET_KEY`; never return them, log them, or place them in API error details. Registry entries retain `runtime_enabled` fixed for the process lifetime. API responses calculate `restart_required = desired_enabled != runtime_enabled`. Config updates increment revision and affect the next submitted job without restart.

Expose admin-only:

```text
GET  /api/admin/plugins
PUT  /api/admin/plugins/{id}/config
POST /api/admin/plugins/{id}/enable
POST /api/admin/plugins/{id}/disable
```

- [ ] **Step 3: Define job states and partial unique index**

```python
class PluginJobStatus(StrEnum):
    QUEUED = "queued"
    REQUESTING = "requesting"
    SUCCEEDED = "succeeded"
    FAILED = "failed"
    INTERRUPTED = "interrupted"
    CANCELED = "canceled"

Index(
    "uq_active_plugin_job_dedupe", "dedupe_key", unique=True,
    sqlite_where=text("status IN ('queued','requesting')"),
)
```

Store plugin/action, actor, context type/ID/version, config revision, sanitized input snapshot, result Markdown/patch JSON, error code/message, timestamps, and optional `rerun_of_id`. Never store an API key in input or result snapshots.

- [ ] **Step 4: Make submission race-safe**

Build `dedupe_key` from plugin, action, context ID/version, and normalized user input. Insert and commit; on `IntegrityError`, roll back and select the active row by key. This is the only duplicate resolution path—do not rely on an earlier SELECT. Completed, failed, interrupted, or canceled jobs never block an explicit rerun.

Expose:

```text
GET  /api/plugin-actions?target_type={type}&target_id={id}
POST /api/plugin-jobs
GET  /api/plugin-jobs?status=&plugin_id=&limit=&cursor=
GET  /api/plugin-jobs/{id}
POST /api/plugin-jobs/{id}/rerun
POST /api/plugin-jobs/{id}/cancel
```

`/api/plugin-actions` returns only runtime-enabled, desired-enabled actions whose target scope matches. A newly submitted job returns `201`; an active duplicate returns the existing representation with `200`.

```python
async def test_startup_resumes_queued_but_interrupts_requesting(session, worker):
    queued = make_job(session, status="queued")
    requesting = make_job(session, status="requesting")
    await worker.recover()
    assert session.get(PluginJob, queued.id).status == "queued"
    assert session.get(PluginJob, requesting.id).status == "interrupted"


async def test_worker_rejects_changed_config_revision(session, worker, queued_job):
    bump_plugin_config_revision(session, queued_job.plugin_id)
    await worker.run_once()
    assert session.get(PluginJob, queued_job.id).error_code == "plugin_config_changed"
```

- [ ] **Step 2: Implement atomic claim and recovery**

At startup, mark every `requesting` row `interrupted` with code `process_restarted`; never blindly repeat an external request. Leave queued rows queued. A single worker loop selects the oldest queued job and, before claiming, verifies the plugin is loaded, desired/running state is valid, and its stored `config_revision` still matches. A mismatch fails with `plugin_config_changed`. Otherwise it conditionally updates to requesting, invokes the handler, and commits one terminal state. Cancellation of queued jobs is immediate; requesting cancellation is cooperative and otherwise finishes normally.

- [ ] **Step 3: Integrate with FastAPI lifespan**

Start one worker task after migrations and plugin discovery. On shutdown set a stop event, wait briefly for the loop, cancel the task if necessary, and leave any requesting row for next-start interruption recovery. Tests inject a fake registry and handler; no network call occurs.

- [ ] **Step 2: Build bounded context serializers**

Meeting context includes title, purpose, project, participants, agenda notes, outcomes, comments, amendments, and attachment metadata. With an explicit request selection it may also include bounded UTF-8 content from `.md`, `.txt`, `.json`, `.yaml`, `.yml`, `.log`, and `.py` attachments; PDF, office, image, audio, and other binary files remain metadata-only. Project context adds recent meetings, decisions, actions, and open questions. Cap total text deterministically and report truncation. Never grant filesystem, database session, HTTP client, or callable tools to a plugin handler.

- [ ] **Step 3: Define result and application contracts**

Handlers return:

```python
class PluginResult(BaseModel):
    markdown: str = Field(max_length=200_000)
    suggested_patch: dict[str, Any] | None = None
```

The result page lets a user edit Markdown. `/apply` validates the job action's declared application target and invokes the ordinary meeting/project service with `expected_version`; it records normal activity plus `applied_at`, `applied_by`, and the resulting subject/version on the job. Results never write automatically.
